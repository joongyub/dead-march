# 8단계에서 고친 비싼 함수

스트레스 스테이지(병력 5,000)를 CPU 4배 느린 조건에서 600프레임 돌리며 CPU 프로파일을 떠서, 시간을 많이 쓰는 함수부터 고쳤습니다. 프로파일은 실행마다 ±20% 정도 흔들려서, 고치기 전 빌드와 고친 뒤 빌드를 번갈아 3번씩 돌리고 각 함수의 가장 작은 값을 비교했습니다(`npm run perf -- --profile`이 함수별 표를 `artifacts/profile.txt`에 씁니다).

| 함수 | 원인 | 고친 방법 | 전 | 후 |
| --- | --- | --- | --- | --- |
| 피난처 장면 진입 (`CanvasTexture` 생성) | Phaser `textures.addCanvas`가 만든 캔버스의 픽셀을 GPU에서 다시 읽어 옴 | `art/canvasTexture.ts`로 읽기 없이 등록 (7단계) | 3,795ms | 123ms |
| `DisplayList.depthSort` | 무리 스프라이트가 매 프레임 `setDepth`를 불러 장면 전체를 다시 정렬. 효과 파티클이 일반/가산 블렌드를 섞어 정렬 순서가 자주 바뀜 | 깊이는 인원 수가 바뀔 때만 다시 계산. 효과 풀을 일반 125개, 가산 55개로 나눠 각자 고정 깊이 | 29.2ms (정렬 97회) | 10.7ms (정렬 27회) |
| `GateView.update` | 게이트 숫자 옆 아이콘 위치를 잡으려고 매 프레임 `BitmapText` 너비를 다시 잼 | 글자가 바뀔 때 한 번 재서 저장 | 34.5ms | 13.6ms |
| `Effects.update` | 움직이지 않는 파티클에도 매 프레임 위치·크기·투명도를 다시 씀 (쓸 때마다 변환 행렬이 더러워짐) | 값이 바뀌는 것만 씀 | 43.8ms | 36.4ms |
| `BitmapText.getTextBounds` 호출 수 | 위 게이트 너비 재기 | 위와 같음 | 5,457회 | 4,564회 |
| 자바스크립트 전체 (600프레임) | | | 1,415ms (프레임당 2.36ms) | 1,275ms (프레임당 2.12ms) |

남은 시간의 대부분은 Phaser가 스프라이트를 GPU 버퍼에 담는 부분(`batchSprite`, `bufferSubData`)이고, 이건 그리는 스프라이트 수(최대 200개, 저사양 120개)에 비례합니다.
